# 2026-06-23 契约编目阶段性路线记录

> Internal record. Not normative. 本文记录一次关于 Proto UI 契约编目工作阶段、优先级与版本节奏的讨论。它是阶段性工作计划，不等同于正式的 `D-*` 决策实体、`C-*` 契约实体或发布承诺。

---

## 1）背景

截至本记录形成时，Proto UI 的契约编目工作已经完成了一轮核心概念主线：

- props
- lifecycle
- template / render
- feedback
- event
- state
- expose
- context
- anatomy

这批工作主要集中于理论层，以及理论直接指导的基础测试与实现对齐。它们可以暂时理解为 Proto UI 的核心契约基线：即解释 Proto UI 如何定义信息通路、执行阶段、模板结构、状态、暴露、组件间通信与结构协作。

后续契约编目不会只停留在核心理论层，还会继续进入：

- 原型层：每个官方 `asHook` 与官方原型的行为约束。
- 模块层：runtime/module 实现边界、能力输入输出与错误模型。
- host-cap 层：宿主能力的定义、提供者、消费者、缺失策略。
- 适配器层：官方 adapter profile 与宿主协调权衡。

本记录用于整理短期工作方向，以及 0.2 / 0.3 的大致上车预期。

---

## 2）核心契约收尾范围

当前判断中，相对完整且确实属于一级核心契约但尚未收口的概念，主要剩下：

1. `rule`
2. `asHook`

这里的“一级核心契约”并不表示其他概念不重要，而是指某个概念对所有宿主的适用程度足够高，能够抽象出较稳定的跨宿主共性。一个概念不用它的宿主越少，它的一级程度越高，能抽象的共性也越多。

因此，建议短期核心收尾顺序为：

1. 先编目 `rule`。
2. 再编目 `asHook`。
3. 然后再处理 focus、overlay、hit-participation、interaction-boundary 等概念。

---

## 3）二级概念与特权 asHook

focus、overlay、hit-participation、interaction-boundary 等概念都包含一定程度的一级契约内容，但它们的重头戏通常位于二级。

这类概念不会直接作为 `def` 或 `run` 句柄上的一级 API 出现，而是更常表现为特权 `asHook`：

- 它们消费独特的宿主能力。
- 它们向原型作者提供较高层的组合能力。
- 它们把零散一级概念包装成可复用的原型作者 API。

因此，这些 scope 的编目应放在 `rule` 与 `asHook` 之后。它们既不是纯核心信息通路，也不应完全归入普通原型行为，而是可以被看作“一级概念促生的特权 asHook”。

---

## 4）核心契约之后的优先级

核心契约概念收口后，当前建议优先进入原型层编目。

理由：

- 原型层质量提升最明显。
- 官方原型会直接影响贡献者如何编写新原型。
- 现有原型中已经发现不少行为、结构与质量问题，适合进行系统过筛。
- 模块与适配器内部如何实现，对原型作者的日常编写影响相对间接。

这一阶段的目标不是只补几条测试，而是把多数现有官方原型重新过一遍：

- 明确每个原型的身份与行为边界。
- 为每个原型拆出多条必要契约。
- 建立契约实体、测试实体、具体测试之间的引用。
- 按需重写或校准实现。
- 让后续贡献者新增原型时有明确的质量标尺。

---

## 5）模块、host-cap 与适配器的长尾

模块实体、host-cap 实体与适配器契约属于后续长尾工作。

当前优先级判断：

1. Proto UI 模块契约优先于适配器契约。
2. host-cap 编目需要与模块契约协同推进。
3. 适配器契约中，Web Component adapter 由当前主线优先负责。
4. React 与 Vue adapter 的系统编目可交由对应维护者推进。

模块与 host-cap 的价值在于解释实现层真相：

- 某个 module 提供什么能力。
- 某个 module 依赖哪些 host caps。
- host cap 的提供者、消费者、缺失策略是什么。
- 不同 module 之间如何组合而不互相污染边界。

适配器契约的价值在于记录 translation layer 的宿主权衡：

- lifecycle 如何映射。
- props/event/template/feedback/context/expose 如何落到宿主。
- 哪些行为属于官方 adapter profile 的强保证。
- 哪些行为属于宿主能力不足时的优雅降级。

## 6）版本节奏预期

Proto UI 当前以约 3 个月为周期开放新的版本分支。旧分支会从活跃维护逐步进入停止更新、停止修复与废弃状态。

当前版本节奏预期：

- 最新版本：`0.1`
- 下一次发版窗口：8 月中旬
- 目标版本：`0.2`

阶段性上车预期：

- `0.2`
  - 核心契约收口。
  - `rule` 与 `asHook` 完成核心编目。
  - focus、overlay、hit-participation、interaction-boundary 等概念至少完成主要方向梳理。
  - 原型层系统过筛尽量赶上。

- `0.3`
  - 模块实体编目。
  - host-cap 实体编目。
  - 适配器契约系统化，尤其是 Web Component adapter profile。
  - React / Vue adapter 编目可由对应维护者分线推进。

这些预期不等同于正式发布承诺，应随维护者同步与实际工程负载调整。

---

## 7）阶段性里程碑

一个重要里程碑是：

> 契约实体成为真相源，旧契约文档归于历史档案。

达到该里程碑后：

- 新讨论应优先落到 spec 实体体系中。
- 旧契约文档只作为历史背景，不再作为行为真相源。
- 实现、测试、官网文档都应能追溯到契约实体。
- 新贡献者可以通过契约实体理解原型、模块与 adapter 的行为边界。

---

## 8）暂不解决的问题

以下问题本记录不定案：

- `module` 实体的最终 schema。
- `host-cap` 实体的最终 schema。
- `adapter profile` 实体是否在 0.2 前预留，还是 0.3 再正式落地。
- `prototype` 实体的命名、编号与继承关系。
- focus、overlay、hit-participation、interaction-boundary 与 `asHook` scope 的最终关系图。
- 旧契约文档归档目录与迁移策略。

这些问题应在后续进入正式决策或 schema 变更讨论。
